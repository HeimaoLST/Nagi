# Nagi product protocol v1

Target contract for the product boundary between MyGo and the TypeScript backend. The implementation baseline is workbench commit `61062552eab0a0a7bac5fa884c2d9a5456361a16`. The shipped execution bridge and its validation history are described in [Pi integration](pi-integration.md). Methods below describe the migration target. Record each implemented slice against its own candidate and actual worker payload.

## Process and wire format

MyGo owns the window, interaction state, connection form inputs before Save or Test, and the subprocess lifetime. The TypeScript backend owns persistent Bot identity, conversation bindings, activities, captured settings, product commands, tool effects and delivery receipts. Its execution module calls the pinned Pi SDK in process. Pi owns session transcripts, execution and tool scheduling. Product tools invoke the backend's product handlers in process.

Use UTF-8 JSONL over one subprocess's stdin and stdout, one compact envelope and LF per frame, with an 8 MiB limit including LF. Send diagnostics on stderr and exclude credentials. Keep a single ordered writer per pipe with bounded buffering. Allow multiple outstanding requests and out-of-order responses. A malformed frame or a broken pipe ends that connection. The Go supervisor correlates pending calls by connection generation and string request ID, then collects the child's actual exit and waits for its callbacks to finish. Expiry of a local RPC wait leaves the product operation eligible for readback. Only an explicit targeted Stop asks the backend to cancel work.

The frame version `v` identifies the envelope. The initial `app.open` request uses envelope `v:1` and carries `supportedVersions` for the product payload. The backend returns the selected product version, an opaque `streamId`, the initial projection and its `eventSeq`. An incompatible version yields `unsupported_version` before product commands can run. Results and errors use the existing mutually exclusive `ok` branches. Code picks the action from `error.code` and displays localized copy. Technical diagnostics are optional, sanitized and bounded.

```jsonl
{"v":1,"type":"request","id":"r1","method":"app.open","params":{"supportedVersions":[1]}}
{"v":1,"type":"response","id":"r1","ok":true,"result":{"version":1,"streamId":"s1","eventSeq":0,"snapshot":{"bots":[{"botId":"b1"}],"conversations":[{"conversationId":"c1","botId":"b1","draftRevision":7}],"activeActivities":[{"activityId":"a1","executionId":"e2","question":{"questionId":"q1","revision":3}}],"connection":{"state":"ready"}}}}
{"v":1,"type":"request","id":"r2","method":"conversation.send","params":{"conversationId":"c1","operationId":"op1","draftRevision":7,"text":"Review the report","materials":[]}}
{"v":1,"type":"response","id":"r2","ok":true,"result":{"operationId":"op1","state":"accepted","conversationId":"c1","executionId":"e1"}}
{"v":1,"type":"event","streamId":"s1","seq":1,"event":"execution.started","data":{"conversationId":"c1","executionId":"e1"}}
{"v":1,"type":"request","id":"r3","method":"question.answer","params":{"activityId":"a1","executionId":"e2","questionId":"q1","questionRevision":2,"operationId":"op2","text":"Use the draft report","materials":[]}}
{"v":1,"type":"response","id":"r3","ok":false,"error":{"code":"stale_revision","message":"The question revision has changed.","details":{"currentRevision":3}}}
```

Keep one TypeBox definition per method params/result and event payload. Derive TypeScript types and export JSON Schema. Validate incoming requests before dispatch. Go consumes typed product DTOs and decodes event payloads by discriminator. Choose Go generation after checking round trips of optional fields, explicit null values and tagged unions. Opaque product IDs and cursors are strings. Numeric counters and revisions are nonnegative JavaScript-safe integers. Omitted, null and empty values require explicit contracts where they change meaning, including default versus disabled coding tools. An additive optional output member within v1 can be ignored by an older reader. A change to an existing field's meaning requires a new negotiated version.

## Methods

Object field names are wire names. Mutations with durable effects take `operationId`. Writes to editable entities carry the revision of the captured target when needed to prevent stale updates. State returned by a mutation or read is authoritative for its revision.

| Method | Contract |
| --- | --- |
| `app.open` | Negotiate the version and atomically acquire a bounded startup projection and event baseline. Include the active UI targets, Bot and conversation summaries, draft versions, active activities and questions, and nonsecret connection state. Return cursors for collections beyond the startup window. |
| `bot.list`, `bot.create`, `bot.update`, `bot.archive`, `bot.restore` | Page visible or archived Bots. Edits target `botId`, carry the captured profile revision, and return saved metadata or a stable rejection. Archive and restore preserve history and identity. |
| `conversation.list`, `conversation.history` | Page by `botId` or `conversationId`. Return stable public message IDs and timestamps, original user text and required original-content references. Expose unavailable history explicitly. Pi remains the authoritative source for transcript data. |
| `conversation.new`, `conversation.saveDraft` | Allocate a product `conversationId` for the same `botId` or save a specific conversation draft with its context materials and revision. Existing conversations keep their captured configuration and history. |
| `conversation.send`, `conversation.stop` | Send captures `conversationId`, `draftRevision`, exact text, material references and `operationId`. Stop targets `conversationId`, `executionId` and `operationId`. Accepting Stop records the request. The execution can settle as completed if completion won the race. |
| `activity.list`, `activity.get`, `activity.result` | Return activities visible to the given Bot, canonical owner and origin, execution and question state, and the exact execution's text, file references and delivery state. Reopen reads the same result by `activityId` and `executionId`. |
| `activity.continue`, `activity.stop`, `question.answer` | Continue captures the activity, its current revision and explicit materials. Stop captures activity and execution. Answer captures activity, execution, question, question revision, exact answer and materials. A saved answer and its delivery to a live call have separate states. A stale answer cannot target a replacement question. |
| `connection.get`, `connection.test`, `connection.save`, `connection.apply` | Read only nonsecret saved and effective states. Test runs one explicitly requested bounded probe against the candidate config. Save persists the candidate and returns its revision. Apply activates the named saved revision for future contexts. The current combined GUI action needs both outcomes, including Save success followed by Apply failure. |
| `operation.get` | Query the durable receipt by `operationId`. Return the admitted target and outcome known from the store, including pending/unknown outcomes when applicable. |
| `app.shutdown` | Close admission and drain according to the existing application exit behavior. The supervisor observes actual child exit separately from the reply. |

Chat-triggered same-Bot and cross-Bot delegation enter through `conversation.send`. The backend resolves target IDs from scoped product tool calls, captures source conversation/turn, requirements, materials, and ownership, then commits the handoff before starting the recipient. Render artifacts by file reference and read content on demand. Bind the surviving chat, Sources, Settings and contact profile routes to their product callers. The workbench retired its Issue drawer and header actions. History search, full-output copy and result viewing need separate user-facing evidence if another entry point is introduced. Keep Pi context, run and tool-call IDs internal to backend handlers.

## Receipts and events

`id` identifies one call on the live connection. A client-generated `operationId` identifies one user operation within the profile. Persist the intent, method and target before its first possible external effect. Associate admission and execution facts with that receipt, and retain distinct states for pre-admission preparation, accepted execution, known rejection or non-dispatch, and unknown dispatch. A matching duplicate returns the known receipt. An ID used for a different method, target or nonsecret input returns `operation_conflict`; the backend keeps the original operation. Connection requests never retain a secret in their receipt or diagnostics. An accepted response is allowed only after the backend has durably recorded acceptance. No transport timeout or disconnect automatically issues a second mutation. An unavailable receipt yields unknown unless the backend can establish committed non-dispatch. Clear only the draft and material revisions actually submitted, after admitted execution is durably recorded. Preserve newer edits, and retain the captured materials if persistence fails.

Keep four caller-visible facts distinct: the product's command receipt, the execution outcome, the answer or result delivery status, and the activity's business status. A settled execution can be failed, interrupted or completed. A delivered result is durably associated with the origin and exact execution. Notification and readback expose that association. A lost process leaves uncertain effects and unsettled executions unknown. Recovery may read authoritative recorded facts and promote a known result. Unknown work is never redispatched during recovery.

Each event has `streamId` and contiguous `seq` within that stream. `app.open` captures projection and baseline in one committed-state read and queues its response before events for the new stream. The UI discards old stream events after switching streams and applies events by target ID independently of the selected Bot. Durable state events refer to a committed entity revision. Sequence numbers are assigned after coalescing transient text updates. A frame that cannot be queued completes the connection with a visible error. On a gap, reopen and refresh authoritative reads. Active queries and live events reconcile by entity revision so late replies cannot erase later updates. Keep final text, terminal execution status, pending questions and result associations recoverable via reads even if live deltas are lost. History and result payloads use bounded pages or explicit size errors.

## Migration and acceptance

Current interfaces to replace are the execution-shaped worker wire in `internal/pi/client.go` and `internal/pi/worker/`, receipts and store commits in `store.go` and `pi_app.go`, activity control and result handling in `pi_activity.go` and `pi_activity_results.go`, in-Go product-tool callbacks in `issue_tool_app.go` and `issue_handoff.go`, and connection policy in `connection_app.go`. Separate from those domain paths, MyGo keeps rendering, navigation, focus, selection and immediate editor state. Verify all composed UI callers on the chosen candidate. The existing route for Settings → Contact profile is covered on frozen `61062552eab0a0a7bac5fa884c2d9a5456361a16`; that result belongs to the current workbench only.

1. Pin the current workbench source and the owner of each exact path. Put the method/DTO schema and framing changes through the actual TypeScript and Go subprocess connection. Use a frozen candidate for verification.
2. Move profile write ownership and the conversation/activity/receipt operations together for the live cutover. Preserve the current supported profile's Bot IDs, Pi bindings, history references, draft text and materials, captured settings, requirements, questions, pending sends and effect receipts. Validate an existing profile fixture before committing any format change. Assert native preferences remain usable. A profile has one domain writer. Keep the current supported profile's opaque references intact and report unsupported data at admission.
3. Route the MyGo actions through product requests and project correlated events on the UI actor. Retire the superseded execution RPC, Go domain writer/tool dispatcher and their obsolete callers in the switched product. Preserve the pinned Pi worker dependency and delivery provenance under the existing package gates.
4. Verify with actual pinned SDK execution against a controlled local provider. In one scenario the same Bot holds activity A on a question, runs B and continues chatting, then answers A and stops only B. In a second scenario Bot A delegates a file-backed task to Bot B and can reopen the associated result after restart. Drop the response after durably admitting a send or effect, then query the original `operationId` after restart and count provider calls or file effects to detect replay. Also exercise draft and receipt reload, a save failure, connection revision capture, and real process reaping. The freeze must include both implementations, the exact payload, and the test owner's observed outcomes.

Reuse the current `TestPiAppConnectionAndConversation` checkpoints for original text, entry identity, timestamps and per-Bot history after reopen. `TestPiAppActivitiesAndQuestions`, `TestPiConversationDelegation` and `TestPiAppCrashRecoveryNoReplay` provide existing controlled conditions for the three cross-boundary acceptance cases. The QA owner can adapt the assertions to observe product protocol identities and receipts at the new boundary.
