# Nagi product protocol v1

This contract maps the [desktop user flows](../requirements/desktop.md#v1) to the Go client, TypeScript worker and native MyGo workbench. See [glossary.md](glossary.md) for canonical terminology and [RFC-0001](../rfcs/0001-multi-brain-and-capabilities.md) for planned multi-brain, direct inspection, and capability extensions.

## Process and wire format

MyGo owns the window, interaction state, connection form inputs before Save or Test, and the subprocess lifetime. The TypeScript backend owns persistent Bot identity, conversation bindings, activities, captured settings, product commands, tool effects and delivery receipts. Its execution module calls the pinned Pi SDK in process. Pi owns session transcripts, execution and tool scheduling. Product tools invoke the backend's product handlers in process.

Use UTF-8 JSONL over one subprocess's stdin and stdout, one compact envelope and LF per frame, with an 8 MiB limit including LF. Send diagnostics on stderr and exclude credentials. Keep a single ordered writer per pipe with bounded buffering. Allow multiple outstanding requests and out-of-order responses. A malformed frame or a broken pipe ends that connection. The Go supervisor correlates pending calls by connection generation and string request ID, then collects the child's actual exit and waits for its callbacks to finish. Expiry of a local RPC wait leaves the product operation eligible for readback. Only an explicit targeted Stop asks the backend to cancel work.

The frame version `v` identifies the envelope. The initial `app.open` request uses envelope `v:1` and carries `supportedVersions` for the product payload. The backend returns the selected product version, an opaque `streamId`, the initial projection and its `eventSeq`. An incompatible version yields `unsupported_version` before product commands can run. Results and errors use the existing mutually exclusive `ok` branches. Code picks the action from `error.code` and displays localized copy. Technical diagnostics are optional, sanitized and bounded.

```jsonl
{"v":1,"type":"request","id":"1","method":"app.open","params":{"supportedVersions":[1]}}
{"v":1,"type":"response","id":"1","ok":true,"result":{"version":1,"streamId":"stream-1","eventSeq":0,"snapshot":{"bots":[{"botId":"b1","profile":{"name":"Bot","role":"","purpose":"","instructions":"","workspace":"","codingTools":null},"profileRevision":1,"archived":false,"currentConversationId":"c1"}],"nextBotCursor":null,"connection":{"savedRevision":2,"effectiveRevision":2,"saved":{"wireApi":"openai-completions","baseUrl":"http://127.0.0.1:4321/v1","model":"fixture","contextTokens":65536,"outputTokens":4096,"workingDirectory":"/workspace","maxActiveTasks":3,"credentialPresent":true},"effective":{"wireApi":"openai-completions","baseUrl":"http://127.0.0.1:4321/v1","model":"fixture","contextTokens":65536,"outputTokens":4096,"workingDirectory":"/workspace","maxActiveTasks":3,"credentialPresent":true}}}}}
{"v":1,"type":"request","id":"2","method":"conversation.send","params":{"conversationId":"c1","draftRevision":7,"operationId":"op1"}}
{"v":1,"type":"response","id":"2","ok":true,"result":{"operationId":"op1","state":"accepted","target":{"conversationId":"c1"},"execution":{"executionId":"e1","revision":1,"state":"starting"}}}
{"v":1,"type":"event","streamId":"stream-1","seq":1,"event":"execution.started","data":{"conversationId":"c1","operationId":"op1","executionId":"e1","revision":2}}
```

Keep one TypeBox definition per method params/result and event payload. Derive TypeScript types and export JSON Schema. Validate incoming requests before dispatch. Go consumes typed product DTOs and decodes event payloads by discriminator. Choose Go generation after checking round trips of optional fields, explicit null values and tagged unions. Opaque product IDs and cursors are strings. Numeric counters and revisions are nonnegative JavaScript-safe integers. Omitted, null and empty values require explicit contracts where they change meaning, including default versus disabled coding tools. An additive optional output member within v1 can be ignored by an older reader. A change to an existing field's meaning requires a new negotiated version.

The built worker exports JSON Schema 2020-12 from `dist/protocol.js` as `productWireSchema`. Its `$defs` contains the request and event envelopes, the shared error response, and a success response keyed by each request method. Export it with the payload's pinned Node from the payload directory.

```sh
./bin/node --input-type=module -e 'import { productWireSchema } from "./dist/protocol.js"; console.log(JSON.stringify(productWireSchema, null, 2))'
```

The left Bot Team list opens a management menu on a secondary click anywhere in a Bot row. The editor captures that row’s `botId` for reads and mutations. Global Settings contains app-wide preferences.

## Methods

User actions with durable effects use `operationId`. `expectedRevision` is the caller's observed version of an editable object. List and history methods accept `cursor?` and `limit?` and return `{ items, nextCursor }`, with `null` at the end. Cursors are opaque and bound to the query. A cursor belonging to a different query or an unavailable anchor yields `invalid_cursor`.

This matrix specifies the target. Verification status is recorded separately for the TypeScript worker, Go client, live MyGo caller and frozen product E2E.

Natural-language instructions enter through `conversation.send`. Product tools invoke the backend's activity handlers inside the TypeScript process. Conversations and activities own independent execution contexts and keep their original product IDs. Starting a new conversation preserves work attached to the earlier conversation. Cross-Bot handoff keeps its existing behavior and uses a separate acceptance scenario from the current independent-Bot milestone. Previous chats lists earlier conversations for the selected Bot in pages. On the returned page, conversation.list can include preview and timestamp from the first original user prompt. The preview is a single line of at most 256 UTF-8 bytes. A missing or unreadable transcript leaves those fields absent. The list then uses a localized fallback label. Navigation still uses the original conversation ID. Source chat opens the conversation identified by the activity’s originConversationId. Both use a read-only history view. Returning to the current conversation preserves its unsent draft, materials and send target. Pi context, run and tool-call IDs are internal to the backend.

When a conversation, activity, or private autonomous orchestration generation first binds to a Pi session, the backend orders advertised tool definitions alphabetically and composes initial instructions in cache-friendly prefix order: the 100% static L0 Nagi Bot master template first (with conditional foreground orchestration guidance appended only for `Conversation` sessions, and private non-user orchestration guidance for `OrchestrationActor`), then the per-Bot L1 identity, optional built-in Architect guidance (`Conversation` only), optional behavior instructions, captured canonical working directory, optional sorted `<available_skills>` metadata catalog (resolved for the owning Bot on `Conversation`, `Activity`, and `OrchestrationActor` bindings), and finally the thin L1.5 lasting-rules block. Built-in coding tools resolve from explicit `BotProfile.codingTools` or named `toolPreset` (`none` = `[]`, `readonly` = `find/grep/ls/read`, `workspace` = all 7 coding tools; legacy `null` preserves worker defaults). Conversation actors receive alphabetized `activity_action`, `activity_answer` (requiring exact observed `(activity_id, execution_id, question_id, question_revision)` and explicit current-user-turn evidence, returning `confirmation_required` without mutating when ambiguous), `activity_delegate`, `activity_get`, `activity_list`, `activity_result_read`, `activity_trace_read`, `bot_list`, `conversation_read`, `conversation_search`, per-Bot `memory_*`, and `skill_delete`, `skill_exec`, `skill_list`, `skill_read`, `skill_save`, `skill_test`, and `watch_cancel`, `watch_create`, `watch_get`, `watch_list`, `watch_pause` tools (`skill_read` and `activity_result_read` work even when `codingTools: []`, while `watch_create` with `precheck` stays `proposed`/`grant_required` unless covered by an active matching local grant; M4 classifies `watch_list`/`watch_get` as `readonly` and `watch_create`/`watch_pause`/`watch_cancel` as `mutating`); only active `bot_architect` (`PandoraBox`) conversations also receive `bot_create`, `bot_inspect_team`, and `bot_update`. Private `OrchestrationActor` bindings (`purpose: "orchestration"`, `SessionManager.inMemory`, `<orchestration_event>` wake envelopes, `utility` routing default, zero disk JSONL writes and zero `nagi-turn-v1` appends) run without user-turn-only `activity_answer` or `activity_action(steer)` and add alphabetized `conversation_notify` (bounded redacted product timeline notice), `orchestration_request_decision` (`needs_decision` non-blocking card), and `orchestration_finish` (structured checkpoint and causal progress state), recording M4 admissions inside `orchestration_admissions` without mutating foreground `executions`. Both Conversation and Activity (and authorized OrchestrationActor) bindings whose resolved `codingTools` (defaulting to the worker's `defaultCodingTools` when `null`) include `bash` also receive alphabetized `session_close`, `session_eof`, `session_list`, `session_open`, `session_read`, `session_resize`, `session_signal`, `session_watch`, and `session_write` (`none`/`readonly` omit session tools and fail runtime checks with `scope_denied`); handle creation binds to `(creatingOperationId, ownerBotId, originConversationId?, originActivityId?, canonicalCwd, epoch)` so mutations/watch controls fail closed with `scope_denied` outside the exact creating actor while owning-Bot foreground Conversations can read/list, canonical `ICANON && !ECHO` / bounded prompt heuristics enforce non-secret `authPause` without requesting passwords in chat/prompts, and M4 pre-dispatch admission classifies `session_list`, `session_read`, and `session_watch(list)` as `readonly` and all other `session_*`/`session_watch(arm|cancel)` actions as `mutating`. Foreground `Conversation` executions project one frozen, redacted, XML-escaped ephemeral `<active_activities>` whiteboard (<= 5 items, <= 1,536 UTF-8 bytes post-escaping) by editing the SDK-cloned current-run user message in place via Pi's `context` hook (with `supportsMidConvoSystemMessages` enabled on foreground registrations) without mutating `systemPrompt` or persisting any whiteboard bytes into Pi JSONL, `nagi-turn-v1`, or public history. Activity actors receive alphabetized `activity_ask` (supporting optional structured `options[]`, `allow_free_text`, `requires_user_decision`, and allowlisted typed low-risk `preference_key` resolved strictly against user-approved `manual`/`approved` rules with SQLite v9 `activity_triage_accounting`, CAS commit, tool-less fetch credential guard, and `bot_auto` vs `user` provenance), `activity_progress` (`readonly` admission class, rate-limited auxiliary `activity_progress` table with independent `progressSeq`), `activity_result_read`, `activity_trace_read`, `conversation_read`, `conversation_search`, owner-scoped read-only `memory_search_log`, and `skill_exec`, `skill_list`, `skill_read`, `skill_test` (bound strictly to the execution's captured canonical `cwd` and M3 Seatbelt/approval gates; no `skill_save`/`skill_delete`, no memory mutations, no recursion, no Architect tools), strictly scoped to their `originConversationId` and admission-verified direct-owner `grantedLinkedActivityIds` (missing and unauthorized IDs return uniform `scope_denied`). All read-only projections use a credential-independent bounded transcript reader and one shared `streamingProjectionRedactor` across all retained connection and MCP vault keys before search matching, UTF-8 truncation, spill-file writes, trace persistence, or model output. Existing and imported bindings keep their captured L0 and L1 profile instructions verbatim during hot turns (zero mid-session KV cache invalidation); on cold reload or explicit rule/mount refresh, only the `<available_skills>` catalog and L1.5 lasting-rules blocks refresh on the same Pi transcript while preserving captured L0+L1 identity bytes intact. Post-settlement background consolidation records completed activity work logs and recurring-preference review candidates without blocking replies or app exit. Bot profile edits affect instructions for future bindings.

`connection.get` exposes `credentialPresent` with the nonsecret settings. Save and Test resolve an empty or whitespace-only `apiKey` from the currently saved credential source. If that source has no usable key, both return `invalid_params`. A Test error redacts the key used for the probe.

## Receipts and events

`id` identifies one call on the live connection. A client-generated `operationId` identifies one user operation within the profile. Persist the intent, method and target before its first possible external effect. Associate admission and execution facts with that receipt, and retain distinct states for pre-admission preparation, accepted execution, known rejection or non-dispatch, and unknown dispatch. A matching duplicate returns the known receipt. An ID used for a different method, target or nonsecret input returns `operation_conflict`; the backend keeps the original operation. Connection requests never retain a secret in their receipt or diagnostics. An accepted response is allowed only after the backend has durably recorded acceptance. No transport timeout or disconnect automatically issues a second mutation. An unavailable receipt yields unknown unless the backend can establish committed non-dispatch. Clear only the draft and material revisions actually submitted, after admitted execution is durably recorded. Preserve newer edits, and retain the captured materials if persistence fails.

Keep four caller-visible facts distinct: the product's command receipt, the execution outcome, the answer or result delivery status, and the activity's business status. A settled execution can be failed, interrupted or completed. A delivered result is durably associated with the origin and exact execution. Notification and readback expose that association. A lost process leaves uncertain effects and unsettled executions unknown. Recovery may read authoritative recorded facts and promote a known result. Unknown work is never redispatched during recovery. SQLite v7 records authoritative pre-dispatch tool admission (`execution_mutation_admissions`, `execution_admission_coverage`) via the pinned Pi `tool_call` hook before local or MCP dispatch, treating `write`/`edit`/`bash`, all MCP tools (regardless of annotations), skill scripts, and unknown tools conservatively as `mutating`; automatic silent escalation (`activity_escalations`, `maxEscalations = 1`) requires a terminal prior utility failure, recorded coverage with zero admitted mutations, and durable preservation of the original execution and trace, while any admitted or uncertain mutation transitions directly to `needsAttention` with zero silent replay.

MyGo commits the ID and target of a user action in its local recovery state before its first possible dispatch. TypeScript owns the product receipt, including the captured method and target. On restart an absent receipt leaves the caller's operation unknown unless non-dispatch can be established. Duplicate requests are resolved before mutable revision checks. A durable accepted receipt can refer to a starting execution. Only observed Pi execution admission clears the exact submitted draft revision. A known accepted receipt survives an unknown execution outcome.

Each event has `streamId` and contiguous `seq` within that stream. `app.open` captures projection and baseline in one committed-state read and queues its response before events for the new stream. The UI discards old stream events after switching streams and applies events by target ID independently of the selected Bot. Durable state events refer to a committed entity revision. Sequence numbers are assigned after coalescing transient text updates. A frame that cannot be queued completes the connection with a visible error. On a gap, reopen and refresh authoritative reads. Active queries and live events reconcile by entity revision so late replies cannot erase later updates. Keep final text, terminal execution status, pending questions and result associations recoverable via reads even if live deltas are lost. History and result payloads use bounded pages or explicit size errors.

Events and replies may arrive in either order. Deduplicate by operation and execution IDs, and reconcile durable state by revision. `execution.textDelta` identifies the UTF-8 byte offset for its text in the current execution. Reads expose a bounded active text prefix and its byte length, or mark it unavailable. Final text is obtained from conversation history or the exact activity result.

## Current profile admission

The worker opens product mode with explicit absolute `--product-profile <contacts.json>` and `--credentials <connection.json>` paths, alongside `--state-dir`. It stores live product records in `nagi.db` using versioned SQLite migrations. A nonstandard profile filename uses `<profile>.sqlite`. The first open validates and imports an existing v1 or v10 JSON snapshot. The caller explicitly enables `--fresh-product-profile` after observing that the selected path is missing.

The worker commits each update to SQLite before publishing `contacts.json` as a recovery snapshot. It records the snapshot digest in SQLite and can finish interrupted publication on reopen. A matching or missing snapshot loads the SQLite state. A different snapshot must validate before it can replace the SQLite records. A damaged snapshot stays in place so Settings can restore it from a recovery copy.

| Current stored records | Product representation |
| --- | --- |
| Stored v10 Bot records, current and previous Pi bindings, selected Bot | Bot identity and current/read-only conversation IDs. Existing Pi context, session and captured configuration associations are retained. Native preferences carry the existing selection, layout, theme IDs, appearance and optional `hideBuiltinArchitect` sidebar visibility preference. |
| Draft and pending send | Exact draft text and saved material snapshots. Pending sends use known operation and execution IDs from the original scope where available. An uncertain send remains unknown and is never submitted during admission. |
| Activities, questions, recorded operations and handoffs | Activities preserve execution IDs, questions and receipt associations. Imported questions require a verified original execution. Handoffs require the original source conversation session, Bot and issuing turn. Admission rejects unresolved or mismatched associations before replacing the original file. |
| Saved v2 connection and captured source records | The private credential file remains the source of keys. The product profile retains nonsecret configuration versions and credential source IDs. No key enters a receipt or returned projection. |

An unanswered question can omit `delivery`. A saved answer returns `saved`. Delivery transitions through `dispatching`, then `delivered` when Pi confirms the exact tool result, or `unknown` when delivery is unsettled. When a paused `waitingForAnswer` Activity's captured Provider credential is revoked or deleted, `question.answer` persists the answer atomically as `{ answerSaved: true, delivery: "saved", deliveryBlocker: "credential_unavailable" }` (idempotent on duplicate `operationId`, never silently falling back to another Provider and never resurrecting an `unknown` execution across restart). An imported known cancellation retains `canceled`. Restart preserves `saved`, `delivered`, `unknown`, `canceled` and the absence of a receipt. Only an unsettled `dispatching` state resolves to `unknown` on restart.

`main.go` opens the selected profile through the product client before rendering the workbench. The initial snapshot and conversation reads restore each Bot’s draft, captured materials and current conversation ID. The app reads the selected Bot’s history before the first frame. `contacts.json.ui.json` holds the selected Bot, native presentation preferences and pending operation lookup markers. The worker owns the profile and private credential files. After initial profile admission fails, an explicit Save or Apply can retry the configured profile. A failed retry preserves the original bytes. An exited worker must be reaped before its replacement opens the profile and reads durable state by its original IDs. Reopening never submits a captured send.

The recovery copy contains the product profile and its saved workbench state. Pi transcript references and result-file paths still point to their original storage. Restoring on the same installation therefore depends on the existing Pi state directory and workspace files. Private connection credentials stay in the separate connection file. Recovery validates execution ownership against recorded receipts and preserved import metadata. Older v1 copies can contain imported executions with no receipt or independent owner. For those rows the copy must name exactly one owning activity. A move to a different sole activity cannot be detected from that copy.

Settings offers restore when the current profile is unreadable. After the user selects a compatible copy and confirms, Nagi preserves the damaged bytes in a separate file, rechecks the target and installs the copy. On reopening, it reads the restored state without dispatching pending operations. A failed readback after installation leaves the outcome unconfirmed.
