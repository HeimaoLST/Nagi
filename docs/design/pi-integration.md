# Pi product integration

This is the current migration contract for [Nagi #31](https://github.com/HeimaoLST/Nagi/issues/31). The native Qoder-derived interface and product requirements remain authoritative in [desktop.md](desktop.md) and [the requirements](../requirements/desktop.md). This contract replaces execution-specific Saki assumptions; it is not an acceptance report.

## Source and product boundary

Remote dev `833403e1248e131dab09be254f17f1b8db4434b0` is an ancestor of PR30 `57e0a6784ba7f8ec4c37e5a76f6ab8cdccd9542c`. Integration inherits both, including PR30's Settings and single-list sidebar. PR30's historical timeout is not Pi evidence. Development now uses the canonical Nagi checkout on dev. Integration/E2E uses the separate integration worktree at a frozen committed candidate; main is the stable-release line. Extra task worktrees have explicit owners and cleanup conditions. Reserved preview apps and user profiles remain outside routine source cleanup.

Pi 1.5.2 owns model execution, coding tools, compaction and session transcripts. Nagi owns Bot identity, conversation/activity routing, admission, questions, product ledgers and durable effect receipts. A Bot can have concurrent conversation and activity contexts. This does not select a permanent parent/child hierarchy, autonomous clones, branch naming or a fork policy. Finishing a conversation turn or switching the selected contact does not cancel admitted activities. App-off continuation, a daemon and a general scheduler are outside scope.

There will be one concrete Pi implementation, not a backend interface or permanent fallback to Saki. During migration, an incomplete Draft must remain visibly incomplete. Legacy-history reading is reserved pending the user's explicit archive-versus-readable choice; do not remove that capability or reinterpret its references while the choice is pending. This holds legacy-data activation and reader deletion, not unrelated product wiring or isolated fresh-data E2E.

## Owned process and typed IPC

One Go `pi.Client` owns one pinned Node worker for the app. It starts with explicit worker/state paths and receives configuration over stdin; keys never appear in argv or diagnostic output. Package startup resolves its own Resources, independently of PATH. Development overrides are explicit and are not a consumer prerequisite. Build the worker with scripts/build-pi-worker.py using an explicit verified runtime input and fresh output outside the checkout; its payload includes the pinned Node, compiled entry, production dependencies and full notices. The builder installs the full locked dependency set externally, compiles there, records the actual compiler inputs and removes development dependencies before delivery. npm development dependencies are not a shipped runtime requirement. Stdout is protocol only; diagnostic stderr must not contain credentials or model text by default.

The pinned worker ready envelope includes required `builtinCatalog` metadata: ordered supported coding tools with names/descriptions, plus a separate default-name subset. The worker derives supported metadata from the public Pi tool definitions; its current defaults are `read`, `bash`, `edit`, `write`, while `grep`, `find`, `ls` are additional supported choices. The client rejects missing or malformed catalogs. These facts identify supported/default selections for future contexts, not executable availability, active-context tools or provider/MCP readiness. A profile selection remains null/default, an explicit empty array/no coding tools, or an explicit supported subset.

Only the current live host/generation publishes its catalog after Apply. Reconfiguring that same live host does not replace an existing context's captured tools or settings. Exit invalidates catalog readiness; recovery uses the existing Apply action after the old worker is reaped, callbacks complete and its exit has reached the UI actor. It does not replay unknown work or launch the retired Runtime catalog loader. This source contract still requires actual-worker/profile evidence on a frozen replacement payload.

Numeric token limits and selection revisions must fit JavaScript exact integers (at most 9007199254740991); reject unrepresentable values rather than rounding a host integer or guessing a provider limit. Keep the raw GUI draft and its error.

The private JSONL request envelope is `{v:1,id,method,params}`. Responses are `{v:1,type:"response",id,ok,result}` or the same with `error:{code,message}`. Events are `{v:1,type:"event",workerEpoch,contextId,runId,seq,event,data}`. IDs are nonempty Nagi correlations, not provider-generated identifiers. Responses correlate by request ID; events correlate by epoch/context/run and increasing sequence. The maximum frame is 8 MiB including LF, matching the current product boundary; history is paged rather than silently shortened to fit. A malformed frame or unexpected EOF fails pending requests and leaves admitted unsettled runs unknown. No automatic command replay follows a timeout/disconnect.

| Method | Params and observable result |
| --- | --- |
| `configure` | `wireApi` (`openai-completions` or `openai-responses`), `baseUrl`, `apiKey`, required opaque `credentialSource`, `model`, positive `contextTokens`/`outputTokens`. Installs new-context defaults only and returns their source ID, SDK version and worker epoch. It does not retarget existing contexts, test a provider or establish MCP readiness. |
| `context.open` | `contextId`, `botId`, `purpose` (`conversation`/`activity`), optional `activityId`, `selectionRevision`, `instructions`, absolute `cwd`, optional `resumeRef`, `used`, `codingTools`, `domainTools`, optional `mcpServers` and full `configuration`. Returns the exact binding and opaque reference. Each domain tool has name/description/JSON-schema parameters; its effects remain in Go. Each MCP entry has `name`, immutable host-owned `sourceId` and an SDK `config` object. |
| `context.history` | `contextId`, optional stable entry cursor and bounded page limit. Returns SDK public entries, session identity, next cursor and projection metadata. Rendering uses original text/tool results; no direct journal read. |
| `context.configuration` | `contextId`. Returns actual nonsecret `contextId`, `wireApi`, `baseUrl`, `model`, `contextTokens`, `outputTokens`, `credentialSource`, `credentialPresent` and SDK `activeTools`. No key is returned. |
| `context.configure` | `contextId`, `settings:{model,contextTokens,outputTokens}`. Idle target only; changes only that context model/limits, retaining its endpoint/wire/credential source and tools. Returns actual configuration; other active contexts are untouched. A failed/lost update may have committed: read configuration once, never replay the write automatically. |
| `context.inspect` | `contextId`. Returns actual public model context, finalized messages, separate partial streaming state, active run, observation sequence and captured time. This is the public SDK context projection, not a claim of byte-identical provider request serialization after hooks. A bounded result must disclose incompleteness; it cannot claim a complete snapshot after truncation. No model request is made. |
| `run.start` | `contextId`, unique `runId`, exact text and captured product turn/execution correlation. Returns admission before asynchronous execution. Already-busy contexts reject without a queue. The Go product owns global capacity and conversation reservation. |
| `run.cancel` | Exact `contextId`/`runId`. Acknowledges cancellation request only; settlement is a separate event. It must not abort another context. |
| `tool.result` | Exact epoch/context/run/call ID and success content or error. Resolves only that pending custom-tool Promise. Stale/duplicate answers never target a newer call. |
| `context.close` | Idle context only, with awaited extension/session disposal. Does not delete its session data. |
| `shutdown` | No new admission; caller has completed product drain. Await SDK runtime disposal, flush protocol and exit. Go exports the actual wait/reap result separately from app exit. |

Events include `run.started`, `text.delta`, `tool.request`, `tool.finished` and `run.settled`. A custom `tool.request` carries tool name, exact arguments and call identity; Go asynchronously invokes the existing actor/domain handler and returns `tool.result`. Neither the pipe reader nor UI actor waits synchronously for another context's completion. A settled event includes completed/interrupted/failed outcome, finalized assistant text/error and public usage when available. An accepted request, a successful tool receipt, a settled run and a completed business issue remain distinct.

SDK session methods provide history and compaction-aware context. Check file metadata before the mutating SDK open: a used missing/empty reference is unavailable and its original bytes remain untouched. Only durably proven-unused missing/empty bindings may receive a new reference; do not repair the old file. A used or uncertain missing session fails visibly. Pi execution IDs are correlated with Nagi's existing execution ledger; old task/message fields must not be populated with invented provider facts. Current streaming text is not a finalized outcome.

## First use, tools and questions

A new user opens native Settings, chooses Chat Completions or Responses, enters endpoint/key/model, chooses a working folder, then uses Save and Apply. Preserve working token/slot defaults and expose them as advanced controls; positive IPC values do not require first-time users to learn token-window settings. Exact raw Draft ownership, errors, saved defaults and effective context settings remain separate. Test is an explicit tools-disabled bounded request, not a side effect of Save/Apply. Existing two-slot default supports a chat and one activity; the two-activity-plus-chat acceptance scene explicitly configures three slots rather than silently changing the user's value.

Each context captures its full connection/model snapshot at open and owns an isolated SDK ModelRuntime/credential store. The host supplies a nonempty immutable credentialSource ID for its endpoint/wire/key snapshot; it is generated by Nagi, not entered by the user or inferred from a key hash. Reusing a live source ID with different endpoint/wire/key is a conflict. Keys travel only into the worker and remain outside history/readback. Public SDK custom binding metadata contains the nonsecret configuration/source only; used reopen must match the captured snapshot, including after defaults change. The Nagi private connection owner must resolve that source for restart; missing source is unavailable, not permission to use a new default. Product persistence activation remains fenced pending its data contract.

The worker registers an owned provider and explicit credential store; it must not inherit unrelated user Pi profiles. GUI limits are user declarations, not discovery or verified pricing. Automatic model retry is disabled for this initial cutover; uncertain sends are not replayed. Pi compaction stays SDK-owned. Use the configured output reserve and preserve the current product recent-context budget min(8192, (context minus output) / 4); this is a product policy, not discovered provider capacity. Usage scope and unknown pricing must be reported honestly; no host transcript rewrite or model-generated title call is added.

Coding tools use actual Pi read/bash/edit/write in the selected project cwd, plus explicitly supported optional tools. Nil/default and explicitly empty selections remain distinct. Domain-tool registration is separate so disabling coding tools does not accidentally disable Nagi's promised coordination tools. Conversation tools retain issue_list/get/action semantics and existing scope/operation receipts; activity question handling retains issue ownership and exact question identity. The current conversation bridge is `piIssueTools`: open the real context with `piIssueToolDefinitions()`, construct it from the returned binding and exact `StartRunParams`, and install `HandleEvent` before starting the run. Admission requires the matching `run.started` correlation and captured active product scope. Dispatch uses the existing actor/domain handler and operation ledger. Callback errors require the host to cancel or stop that run; `Drain` closes admission and finishes off the actor while the actor/client remain available. Worker shutdown/wait and callback draining remain separate host obligations. This unit does not wire application startup, activity `issue_wait`, or a held activity question. Direct progress inspection reads public context/state without asking the activity model to generate a report.

For a question, persist the existing question/receipt association before showing it. The GUI captures owner, issue, question reference/revision and origin epoch/context/run/call. Answer uses one shared domain operation, persists the accepted answer, and resolves only that held tool call. A generic supplement save is not an answer. The current Answer form captures the displayed contact, issue, question reference and requirements revision. Its save and the model tool share `answerIssueQuestionFor`; an identical saved answer returns the linked supplement receipt, while a conflicting, stale, superseded or terminal unanswered target is rejected. Persistence failure preserves the prior question/context/receipt and the form draft. Capturing the GUI target alone does not establish the still-pending Pi activity-call correlation. A cancelled or lost question may not be delivered to a replacement run automatically. Keep current legacy wait/cancel semantics until this Pi-specific correlation is wired; no duplicate question state machine is introduced.

General external MCP uses Pi's public MCP extension with Nagi-owned configuration, explicit direct exposure for small toolsets and awaited initialize/list/call/close. Internal Nagi domain tools use the direct callback above. No required user CLI/config file is added. Local worker readiness, external MCP readiness and provider readiness are separate. Real support is claimed only after actual product integration, not from SDK source inspection.

The initial MCP configuration supports explicit absolute stdio commands with literal arguments/environment and optional cwd relative to the selected project, or Streamable HTTP URLs with literal headers. Values are not expanded through ambient variables, shell commands or unrelated Pi files. OAuth/provider-token integration is unsupported until a product-owned authentication flow exists and must fail visibly. The worker selects direct exposure and disables automatic codemode; disabling coding tools does not disable the configured MCP tools. It fixes the SDK's agent-directory setting to its owned state directory and supplies an owned MCP log path; no consumer environment setup or unrelated Pi credential store is used. Session metadata retains server names, opaque source IDs and a canonical full-configuration SHA256 integrity digest. Raw private values stay outside history; the digest does not serve as a source ID. A used reopen must match the captured configuration, including after close/restart; the host retains the private immutable snapshot. These module fields do not activate product persistence or supply a GUI configuration flow by themselves.

Pi remains version1.5.2 with local `patches/pi-mcp-process-events.patch` SHA25648c4c0b7a5c683ac6c37d5f3fbfc3cdd1f09faec8b76a281bd53b86dbf802eb6 and the separate two-index export supplement `patches/pi-memory-credentials.patch`. The runtime pin records both exact digests and before/after SDK hashes. Apply them only in a fresh external payload. The export supplement exposes existing SDK constructors so the worker injects a separate empty in-memory MCP credential store, with no private import or store copy. Empty memory does not disable OAuth protocol; it prevents undeclared persisted credentials from being loaded or sent. Anonymous/static-header HTTP behavior still needs controlled evidence. The added eager import edge is not a loading-cost measurement.

The optional public stdio observer emits `spawn_error`, `exit` and `child_close`; close carries `spawnObserved` and `exitObserved`. The worker forwards these as `mcp.process` events with empty `runId`, context-local increasing sequence, `server`, `sourceId`, `attemptId` and the captured process fields. Only this event may omit a run identity. Ordinary run events keep their existing epoch/context/run sequence validation.

These are direct-child Node observations, not an independently observed OS waitpid or all-descendant termination. Observer invocation is FIFO-microtask scheduled without awaiting returned work; async completions may reorder, callbacks can block and termination can lose events. Existing transport close does not guarantee notification or durable logging completion. Preserve actual null codes/signals and failed-spawn flags instead of inferring success from close. Published upstream source maps remain unchanged for the patched lines. Controlled MCP E2E must exercise real initialize/list/call, normal direct-child exit/close and spawn failure through this production extension before claiming lifecycle support; internal domain receipts and native product acceptance remain separate.
