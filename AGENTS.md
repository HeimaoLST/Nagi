# Nagi contributor instructions

## Product and execution ownership

The product goal is an open-source Bot Team, with Grokbot as the user’s reference. The current priorities are polishing the everyday desktop UI against the design checklist and making multiple Bots work independently. Verify that switching between Bots preserves each one’s conversation, draft, running work and results. Cross-Bot coordination is outside this milestone.

Nagi is the native MyGo product in module `github.com/HeimaoLST/Nagi`. The authorized integration replaces Saki execution with pinned Pi 1.5.2. Pi owns its execution loop, provider integration, tools and authoritative session transcripts. Nagi owns persistent Bot identity, routing, activities, questions, delivery/effect receipts and user interaction. Do not implement another Agent loop or retain two permanent execution implementations. Do not add a generic backend-plugin framework.

Nagi uses only Pi and its current product store. Retire Saki adapters, legacy session readers, old schema migration and dedicated fixtures. Start with the Nagi profile. Preserve current Pi contacts, drafts, receipts, backups and restart semantics. Keep changes and data cleanup confined to the Nagi product; the Saki project is outside this checkout.

Accepted work, execution settlement and business completion are distinct. Switching conversations or finishing a chat turn does not withdraw admitted work. Preserve explicit cancellation, unknown delivery and no automatic replay of uncertain effects. The current scope adds no daemon, app-off continuation or general scheduler. A prototype's hierarchy, permanent naming, fork policy or scripted outcomes are not product decisions.

The UI remains native GPU MyGo, with no HTML/DOM/WebView. Prefer the pinned MyGo component library and matching official examples before writing custom UI. Inspect existing components and shared product helpers first; write only the smallest necessary custom part when the required behavior cannot be expressed by those components, and state that concrete gap. Keep the adopted Qoder base with the user-approved phase1 corrections in [the current visual contract](docs/design/desktop.md#qoder-complete-layout-20261116); the checklist's phase2 style remains a proposal. Preserve current working product capabilities. Ordinary setup must use GUI endpoint/key/model controls, not user environment variables, terminal commands or manual configuration edits. Real credentials must not pass through the lab's known AX-exposed field. Determine the actual product control's behavior before claiming secure entry. Real provider execution needs exact configuration and budget; no such execution follows from offline integration authority.

## Lessons and development practice

Read applicable entries in [lessons.md](lessons.md) before development or changes to a related module. It records concrete mistakes, repeated regressions and user corrections. Update it promptly when an issue is discovered or corrected, as part of development rather than at final handoff. Use concise, precise English and a technical title per entry; retain only `Problem`, `Cause or correction` and `Prevention`. Do not add dates or a separate recurrence log. Mark unconfirmed causes `Unconfirmed`; merge duplicate entries, correct stale conclusions and retain useful context. Check lessons coverage and affected contributor rules before delivery.

Inspect existing callers and implementations before editing. Keep one clear implementation path and conventional names. Avoid speculative abstractions, repeated defensive guards and unrelated repository reorganization. Do not write inline/end-of-line comments or comments inside implementation bodies. Add documentation comments only for necessary caller-visible contracts that naming/types/signatures cannot express; essential independent explanations must stay outside implementation bodies.

Developer TDD and developer-written or modified unit tests are prohibited. Development verification uses real integration/E2E behavior, preferably existing coverage. The test owner alone maintains necessary unit regression coverage. Tests must check observable behavior and meaningful invariants, not constants or removed features unless absence is the contract. Coordinate concurrent integration tests deterministically where practical.

When a feature is explicitly retired, remove its obsolete UI, callers and dedicated tests rather than preserving it as a capability-hold panel. Keep unrelated live configuration and product-data behavior intact.

## Writers and Git

The Nagi lead is the unique repository delivery and Git/integration owner for this migration. The PM coordinates overall direction. Every task binds a source/worktree, exact writer paths and execution authority; recheck stable HC identity/task/status before dispatch. Existing product owners remain unique writers. Workers do not spawn agents, edit another owner's paths, or mutate Git/GitHub without express delegation. Use precise English for briefs, reports and handoffs.

Use `dev` for daily development, `integration` for integration testing and acceptance, and `main` for stable releases. The main checkout is `~/Workspace/Nagi`; the integration worktree is `~/Workspace/worktrees/Nagi/integration`. Keep names short and conventional, without engine names, dates or repeated product/agent prefixes. Preserve PR30's adopted UI history and all product data.

Create additional worktrees when independent features, fixes or validation need isolation. Each temporary worktree and branch must have a lead-assigned owner, purpose, source and completion condition. Do not create one per agent by default. Freeze a committed candidate before validation; the tested worktree must remain unchanged until the result is collected. Coordinate development and validation phases explicitly rather than testing moving source. After completion/merge, stop owned processes and remove obsolete temporary worktrees and branches. The user requested direct deletion of confirmed obsolete resources, without new archives; running apps/profiles, user data and original acceptance evidence remain outside routine cleanup.

Keep team agents visible in named tabs in the same Nagi Space when the user requests a team. Use OMP for the rebuilt team. Use shared DeepSeek Flash for bounded lightweight or mechanical operations, Sol for routine implementation/review and Terra for demanding coding. Keep backend, UI and QA ownership clear when switching models. UI uses Sol as a peer implementation role; the user-created shared Flash operator is separate and must not replace the UI specialist. Reserve Astra for the most challenging tasks or repeated failures by other models; do not spend it on routine inventories. During sustained work, send a consolidated progress report every20minutes with actual completed work, validation, blockers and next actions.

Use coherent commits and normal pushes to reviewable branches/PRs targeting `dev`. Do not force-push, tag, publish Releases or deploy. An incomplete Draft is preferable to weakening required gates or claiming an intermediate build is accepted. Commit/push safe checkpoints; integrate finished work after applicable review and required CI under the established authority. Worktrees and temporary paths are disposable, so essential contracts and validation summaries belong in Git/PR records.

## Validation and delivery

Use `python3 scripts/gui-go.py build|test|vet` to preserve the pinned MyGo patches without changing the module cache. Keep MyGo unchanged unless a concrete required API gap is separately approved. Use explicit-cwd owned HC background programs for long commands and wait with HC. Pass the verified owner with `--parent` and retain actual HC parent/exit metadata separately from a declared task owner. Build outputs and raw evidence stay outside source. Do not reopen old MVP/native/model runs merely because an older task had authorization.

Pi integration requires the actual pinned worker and real product tool bridge against a controlled local provider, with correlated contexts, direct progress reads, targeted question/answer, cancellation, crash/restart/no-replay and child reaping evidence. Package provenance must identify Nagi, Pi/dependency locks and the delivered JS runtime separately. Standalone delivery requires launching with Node absent from PATH. Existing Saki CI results or prototype screenshots do not validate changed Nagi code. Keep the protected aggregate gate and replace obsolete engine checks with actual Pi checks; do not turn missing coverage into a skip/pass.

Keep current requirements/design in the existing topic documents and preserve useful historical evidence through explicit Git links. Remove superseded normative instructions rather than maintaining competing current designs. Distinguish source, build, integration/E2E, native, real-model and human acceptance. Every final report states commands/exits, source identity, observed results and remaining gaps.

Controlled native cases must retain their isolated profile binding on independent app launches, not only in the first parent process environment. Recheck process identity after close observations; a new window is not evidence that the original process stayed alive or drained.

## Required UI review

Read and apply the [UI design checklist](docs/design/ui-checklist.md) for every change that affects what users see or how they interact, including shared components, themes, layout, controls, wording, localization and user-visible state transitions. Follow the [UI review workflow](docs/design/ui-review.md). Freeze the candidate, identify the affected checklist items and shared surfaces, and inspect original screenshots of the actual composed pages against the adopted design and approved phase 1 corrections. Check the affected sizes, themes, languages, data and interaction states from the checklist. Include the full applicable matrix in whole-app acceptance.

Use native-window evidence for §12 and any native claim. Record the actual action and its result when an item depends on interaction. Headless screenshots support rendered appearance claims within their observed scope. Source inspection, geometry and passing tests supplement visual review. Keep evidence tied to the inspected candidate and scene, and keep original files outside the checkout.

Record the reviewer, candidate, checklist results, evidence and open items in the PR or delivery record. Apply §7.2 to the declared scope. Confirmed P0/P1 findings fail review. Missing applicable evidence, unreviewed items or P2 findings without a repair plan leave review pending. Affected UI must pass before acceptance or merge. Draft PRs may retain pending or failed reviews with the findings recorded. The reviewer must inspect the evidence and record a visual verdict.
