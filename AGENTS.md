# Nagi contributor instructions

## Product and execution ownership

Nagi is a native MyGo desktop application for long-lived Bot conversations. Use the [desktop v1 user flows](docs/requirements/desktop.md#v1) for product scope. The left list is the Bot Team. A secondary click anywhere in a Bot row opens management for that row’s stable Bot ID. Keep individual Bot profiles in that flow and global preferences in Settings. Call attached text and files Materials. One Bot can own several activities. Switching Bots, starting a new chat or completing a chat turn preserves already admitted work. Keep each draft, activity, question, cancellation, result and file bound to its recorded owner. Preserve an uncertain operation on restart and never replay it automatically.

The [product protocol](docs/design/product-protocol.md) defines the Go and TypeScript boundary. Pi owns execution, providers, tools and session transcripts. Nagi owns product identity, activity routing, questions, receipts and interaction. Protect current Nagi profiles, supported data admission, backups and reference integrity. App exit drains and reaps the owned worker. Retire fixtures and callers specific to removed features. A stored field, past implementation or old test alone cannot define a new v1 requirement.

MyGo owns native presentation, focus, scrolling, theme and language. Use pinned components and existing shared helpers before adding a custom control. Apply the [desktop design](docs/design/desktop.md) and [UI checklist](docs/design/ui-checklist.md) to the actual pages the user reaches. Ordinary setup must work through the GUI. Verify credential controls with synthetic data; real provider runs require an explicitly authorized configuration and budget.

## Lessons and development practice

Read applicable entries in [lessons.md](lessons.md) and the [code and UI standards](docs/code-standards.md) before development or changes to a related module. It records concrete mistakes, repeated regressions and user corrections. Update it promptly when an issue is discovered or corrected, as part of development rather than at final handoff. Use concise, precise English and a technical title per entry; retain only `Problem`, `Cause or correction` and `Prevention`. Do not add dates or a separate recurrence log. Mark unconfirmed causes `Unconfirmed`; merge duplicate entries, correct stale conclusions and retain useful context. Check lessons coverage and affected contributor rules before delivery.

Inspect existing callers and implementations before editing. Keep one clear implementation path and conventional names. Avoid speculative abstractions, repeated defensive guards and unrelated repository reorganization. Do not write inline/end-of-line comments or comments inside implementation bodies. Add documentation comments only for necessary caller-visible contracts that naming/types/signatures cannot express; essential independent explanations must stay outside implementation bodies.

Developer TDD and developer-written or modified unit tests are prohibited. Development verification uses real integration/E2E behavior, preferably existing coverage. The test owner alone maintains necessary unit regression coverage. Tests must check observable behavior and meaningful invariants, not constants or removed features unless absence is the contract. Coordinate concurrent integration tests deterministically where practical.

When a feature is explicitly retired, remove its obsolete UI, callers and dedicated tests rather than preserving it as a capability-hold panel. Keep unrelated live configuration and product-data behavior intact.

## Writers and Git

The Nagi orchestrator/lead is the unique repository delivery and Git/integration owner. Every task binds a source/worktree, exact writer paths and execution authority; recheck stable HC identity/task/status before dispatch. Existing product owners remain unique writers. Workers do not spawn agents, edit another owner's paths, or mutate Git/GitHub without express delegation. Use precise English for briefs, reports and handoffs.

Use `dev` for daily development, `integration` for integration testing and acceptance, and `main` for stable releases. The main checkout is `~/Workspace/Nagi`; the integration worktree is `~/Workspace/worktrees/Nagi/integration`. Keep names short and conventional, without engine names, dates or repeated product/agent prefixes. Preserve all product data.

Create additional worktrees when independent features, fixes or validation need isolation. Each temporary worktree and branch must have a lead-assigned owner, purpose, source and completion condition. Do not create one per agent by default. Freeze a committed candidate before validation; the tested worktree must remain unchanged until the result is collected. Coordinate development and validation phases explicitly rather than testing moving source. After completion/merge, stop owned processes and remove obsolete temporary worktrees and branches. The user requested direct deletion of confirmed obsolete resources, without new archives; running apps/profiles, user data and original acceptance evidence remain outside routine cleanup.

Keep team agents visible in named tabs in the same Nagi Space when the user requests a team (avoid hidden background subagents). Prefer a lean, conflict-free core team: Orchestrator (Antigravity), a single full-stack Dev writer per checkout (OMP with Codex GPT-6.2-Sol), an independent Reviewer/QA verifier in a visible HC tab (Antigravity, to balance model usage), and the shared DeepSeek Flash scout for bounded lightweight or mechanical operations. Spawn a second parallel Dev worker in its own temporary worktree only for genuinely disjoint parallel tracks. Reserve Astra for the most challenging tasks or repeated failures by other models; do not spend it on routine inventories. During sustained work, send a consolidated progress report every 20 minutes with actual completed work, validation, blockers and next actions.

Use coherent commits and normal pushes to reviewable branches/PRs targeting `dev`. Do not force-push, tag, publish Releases or deploy. An incomplete Draft is preferable to weakening required gates or claiming an intermediate build is accepted. Commit/push safe checkpoints; integrate finished work after applicable review and required CI under the established authority. Worktrees and temporary paths are disposable, so essential contracts and validation summaries belong in Git/PR records.

## Validation and delivery

Use `python3 scripts/gui-go.py build|test|vet` to preserve the pinned MyGo patches without changing the module cache. Keep MyGo unchanged unless a concrete required API gap is separately approved. Use explicit-cwd owned HC background programs for long commands and wait with HC. Pass the verified owner with `--parent` and retain actual HC parent/exit metadata separately from a declared task owner. Build outputs and raw evidence stay outside source.

Pi integration requires the actual pinned worker and real product tool bridge against a controlled local provider, with correlated contexts, direct progress reads, targeted question/answer, cancellation, crash/restart/no-replay and child reaping evidence. Package provenance must identify Nagi, Pi/dependency locks and the delivered JS runtime separately. Standalone delivery requires launching with Node absent from PATH. Keep the protected aggregate gate tied to actual Pi execution and product flows; do not turn missing coverage into a skip/pass.

Keep current requirements/design in the existing topic documents and preserve useful historical evidence through explicit Git links. Remove superseded normative instructions rather than maintaining competing current designs. Distinguish source, build, integration/E2E, native, real-model and human acceptance. Every final report states commands/exits, source identity, observed results and remaining gaps.

Controlled native cases must retain their isolated profile binding on independent app launches, not only in the first parent process environment. Recheck process identity after close observations; a new window is not evidence that the original process stayed alive or drained.

## Required UI review

Read and apply the [code and UI standards](docs/code-standards.md) and [UI design checklist](docs/design/ui-checklist.md) for every change that affects what users see or how they interact, including shared components, themes, layout, controls, wording, localization and user-visible state transitions. Follow the [UI review workflow](docs/design/ui-review.md) and keep the full `TestVisualGuard*` invariant suite green across wide/narrow sizes, Paper/Moss themes and EN/zh-Hans locales. Freeze the candidate, identify the affected checklist items and shared surfaces, and inspect original screenshots of the actual composed pages against the adopted desktop design. Check the affected sizes, themes, languages, data and interaction states from the checklist. Include the full applicable matrix in whole-app acceptance.

Use native-window evidence for native interaction claims. Record the actual action and its result when an item depends on interaction. Headless screenshots support rendered appearance claims within their observed scope. Source inspection, geometry and passing tests supplement visual review. Keep evidence tied to the inspected candidate and scene, and keep original files outside the checkout.

Record the reviewer, candidate, checklist results, evidence and open items in the PR or delivery record. Confirmed P0/P1 findings fail review. Missing applicable evidence, unreviewed items or P2 findings without a repair plan leave review pending. Affected UI must pass before acceptance or merge. Draft PRs may retain pending or failed reviews with the findings recorded. The reviewer must inspect the evidence and record a visual verdict.
